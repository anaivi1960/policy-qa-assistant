# Company Policy Q&A Assistant (RAG with citations)

A small REST service that answers employee questions using **only** the 10 Kestrel Nova
policy documents in `data/policies/`. Every answer cites the document and section it came
from, with a quote that is verified word for word against the source file, and every
sentence of the answer is checked against those quotes. If the documents don't contain the
answer, the service says so instead of guessing.

It implements `API_CONTRACT.md`: `GET /health` and `POST /ask` on port 8000.

## Quick start

Requires Python 3.11+ (developed on 3.14) and an Anthropic API key.

```bash
git clone <this repo> && cd policy-qa-assistant
python -m venv .venv
# Windows: .venv\Scripts\activate      macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # then put your key in .env: ANTHROPIC_API_KEY=...
python run.py                 # listens on http://localhost:8000 (override with PORT=...)
```

The first start downloads the embedding model (about 65 MB, cached in `.cache/`), which
takes about a minute. Later starts take a few seconds.

```bash
curl http://localhost:8000/health
# {"status":"ok"}

curl -X POST http://localhost:8000/ask -H "Content-Type: application/json" \
     -d '{"question": "How much paternity leave do I get?"}'
```

```json
{
  "question": "How much paternity leave do I get?",
  "answered": true,
  "answer": "You get 10 working days of paternity leave at full pay. You must take it within 3 months of your child's birth or adoption, and you can split it into up to two blocks.",
  "citations": [
    {"doc_id": "08_parental_leave_policy", "section": "2",
     "quote": "Fathers and partners receive **10 working days** of paternity leave at full pay."},
    {"doc_id": "08_parental_leave_policy", "section": "2",
     "quote": "It must be taken within **3 months** of the child's birth or adoption and may be taken in up to two blocks."}
  ]
}
```

| Variable | Default | Purpose |
|---|---|---|
| `ANTHROPIC_API_KEY` | (required) | Read from the environment or `.env`. Never committed. |
| `PORT` | `8000` | Port to listen on |
| `ANTHROPIC_MODEL` | `claude-opus-5-5` | Answering model |
| `ANTHROPIC_EFFORT` | `medium` | Reasoning effort |
| `TOP_K` | `6` | Number of sections retrieved per question |
| `GROUNDING` | `on` | Sentence-level grounding check; `off` reproduces v1 behaviour |
| `GROUNDING_MODEL` / `GROUNDING_EFFORT` | `claude-opus-5-5` / `low` | Model and effort for the grounding judge |

Errors follow the contract:
- `422 {"error": ...}` when `question` is missing, blank, longer than 1000 characters, or the body isn't JSON.
- `500 {"error": ...}` when the model provider fails or no key is set. A failure never comes back as a `200` refusal.

## Models used

| Role | Model | Why |
|---|---|---|
| Answer generation | **Claude Opus 5.5** (`claude-opus-5-5`) via the Anthropic API, effort `medium`, JSON-schema structured output | Reliable at following "only use these excerpts" and at copying quotes exactly. Structured output guarantees the response parses. |
| Grounding judge | **Claude Opus 5.5**, effort `low`, JSON-schema structured output | A narrow yes/no task per sentence. Low effort keeps the added latency to a few seconds. |
| Embeddings | **BAAI/bge-small-en-v1.5** (384-dim), run locally with `fastembed` (ONNX) | Free, runs on CPU, about 65 MB, strong on short English retrieval. No second API key and no PyTorch install. |
| Keyword retrieval | BM25 (`rank-bm25`) | Exact-token matching for amounts and policy terms. |

The vector store is an in-memory NumPy matrix. With 48 chunks, a dedicated vector database would add complexity without benefit.

## Design choices

**1. How documents are split: one chunk per top-level section (`## N. Title`).**
The contract cites `doc_id` plus the *top-level section number*, so a section is the natural
unit: each retrieved chunk maps 1:1 to a citation, and no chunk mixes two sections. The
policy sections are short (1–6 lines, one topic each), so fixed-size or overlapping chunks
would only cut sections in half. The document title and section title are added to the text
used for retrieval (for example "Business Travel Policy. Accommodation. …") because many
section bodies don't name their own topic. This gives 48 chunks from 10 documents.

**2. Retrieval: hybrid (dense + BM25), fused with Reciprocal Rank Fusion.**
Embeddings handle paraphrase ("I lost my work laptop" → *Loss or theft*). BM25 handles exact
tokens that embeddings blur, such as `NGN 50,000`, `probation` and `anchor days`. RRF combines
the two rankings by rank instead of by score, so their score scales never need calibrating.

**3. How many chunks are retrieved: `TOP_K = 6`.**
Some questions need two documents (Q11: travel + expenses, Q12: learning + annual leave).
In a retrieval-only check, the lowest-ranked required section was 5th (Q11's expense-approval
section), so 6 leaves a margin of one. Six short sections are about 600 tokens, so recall
costs almost nothing and the model ignores irrelevant excerpts.

**4. How refusal works (two layers).**
1. *Prompted refusal.* The model sees only the retrieved excerpts and is told to answer only
   from them. If they don't contain the answer, it returns `answered: false` with a fixed
   sentence and no citations. It's also told not to fill gaps with general knowledge, and to
   answer a partly covered question while stating which part isn't covered.
2. *Evidence check in code (`app/qa.py`, `app/quotes.py`).* The service doesn't trust the
   model's citations. Every quote is checked against the source file using the graders' rule
   (Markdown symbols and extra whitespace ignored, everything else exact).
   - A quote found under a different section or document than claimed is re-attributed to where it actually is.
   - A quote that isn't in the documents is dropped.
   - If an answer has **no** verifiable quote left, it's turned into a refusal, because an answer we can't back with evidence is treated as a guess.

   `answered: false` always forces `citations: []`.

I deliberately did **not** add a retrieval-similarity threshold for refusal. Top-k always
returns *something*, and on this corpus the similarity scores of unanswerable questions
(≈0.55–0.65) overlap with those of answerable ones such as Q4 (≈0.60). A threshold would have
caused wrong refusals, so the refusal decision rests with the model reading the actual text.

**5. Sentence-level grounding check (`app/grounding.py`, added in v2).**
Quote verification guarantees each *quote* is real, but in v1 an unsupported *sentence* could ride
along with a valid quote for another fact (the Q2 failure below). So after the quote check:
1. The answer is split into sentences. A second model call, the judge, sees **only the verified
   quotes** (each labelled with its policy and section) plus the question. It marks each sentence
   supported or not. A sentence counts as supported if it's stated in the quotes, follows by
   simple logic or arithmetic (for example comparing the user's amount to a limit), or only says
   the documents don't cover something.
2. For an unsupported sentence, the judge proposes a **minimal-deletion rewrite**: the same
   sentence with only the unsupported words removed. Rewrites are checked again in one more judge
   call and used only if they pass. Otherwise the sentence is dropped.
3. Citations that no remaining sentence relies on are dropped. If no sentence survives, the
   answer becomes a refusal.

It fails closed: a sentence without an explicit "supported" verdict is removed.

**6. Staying within the 60-second limit.** Worst case: generation (17 s timeout, one retry),
then up to two judge calls (12 s each), about 58 s. Measured latency in v2 was 1.4–10.5 s per
question (median 6.4 s for answered questions), up from 1.6–6.3 s in v1. Refusals skip the judge.

### How I got here: three versions, all reported

| Version | What it is | Official 15 (final run) | Repeat runs | Extra set (15) |
|---|---|---|---|---|
| **v1** | Quote verification only | 11 correct, 3 refusals, **1 partially correct (Q2)** | Q2's failure in 1 of 4 runs | 9 + 6, 0 failures |
| **v2a** | + grounding check that **deleted** unsupported sentences | 11 correct, 3 refusals, **1 incorrect (Q5)** | 2 more runs: 12 + 3 each | 8 + 6, **1 failure (e4)** |
| **v2b** (final) | + judge sees each quote's policy and section; **minimal-deletion rewrite**, checked again | **12 correct, 3 refusals, 0 failures** | 2 more runs: 12 + 3 each | 9 + 6, 0 failures |

Archived results: [`eval/v1/`](eval/v1), [`eval/v2a/`](eval/v2a), [`eval/v2b_repeats/`](eval/v2b_repeats).

- **v1's failure, Q2 (partially correct).** The core answer was right and cited (up to 5 days,
  used by 31 March). But the model added *"unused study days ... cannot be carried over"*, which
  **no policy states**: the learning policy only says unused learning *budget* doesn't carry over.
  It got through because v1 verified quotes, not answer sentences. My auto-grader also missed it
  (it checks that required facts are present, not that nothing extra was added); I caught it on
  manual review. It was intermittent (1 of 4 runs).
- **v2a, the first fix, made things worse in a different way.** It deleted unsupported sentences
  whole.
  - In **Q5** the judge correctly objected to "requested … *through the Travel Desk*" (the policy
    says trips are *booked* there, not requested there). But deleting the sentence also deleted
    "21 days", leaving *"If you request later than that…"*: **incorrect**.
  - In the extra set (**e4**, gym membership) the judge rejected naming the "Expense
    Reimbursement Policy" because a document title isn't part of a quote, cutting the answer to
    a bare "No.".
- **v2b fixed both by design, not by special-casing those questions.** The judge now sees which
  policy and section each quote comes from, and it proposes a rewrite that removes only the
  unsupported words. That rewrite is checked again before use.
- **Replay test** ([`eval/grounding_regression.py`](eval/grounding_regression.py), results in
  `eval/grounding_regression.json`). The v1 failure appeared in only 1 of 4 runs, so a fresh run
  can't prove it's fixed. This script feeds the **exact archived answers** to the real judge, 3 times each:
  - v1's Q2 sentence is trimmed to *"Note that unused sick days cannot be carried over"* in 3/3 runs.
  - v2a's Q5 and e4 answers come out correct in 3/3 runs.
  - The 11 v1 answers that were already correct pass **untouched in 33/33 checks** (no false removals).
- **In live runs** the check changed 3 answers out of 60 requests, and each change removed only
  the unsupported words:
  - Q2 (repeat run 2): *"sick days and study days are separate"*.
  - Q5 (repeat run 2 and the final run): *"through the Travel Desk"*.

**How outcomes were graded:**
- `eval/answer_key.json` was written from the policy text **before** the assistant was first run.
  It lists the required facts and the doc#section each answer must cite.
- `eval/evaluate.py` auto-grades against that key and re-checks every quote verbatim against the source file.
- I then **read every answer and quote by hand** for each final run (v1, v2a, v2b).
  - Manual grades in `eval/review.json` apply only to the exact answer text that was reviewed,
    so a new run can't inherit an old judgement.
  - In the v2b final run, Q2, Q5 and Q11 carry notes. Q11's second document is retrieved only at
    rank 5 of 6, which is a real fragility.
- **Extra robustness set** ([`eval/extra_questions.csv`](eval/extra_questions.csv), written by me,
  **not** part of the official 15). It includes:
  - near-miss unanswerables (bereavement leave, mileage rate, dress code, resignation notice, salary increase)
  - a prompt-injection attempt
  - trick questions that *are* answerable (sick-day carry-over, gym membership, grade-6 overtime)
  - a half-answerable question (allowance amount yes, taxation not covered)

**Honest caveats:**
- **v2b was designed after seeing v2a's failures, on the same 15 questions.** The changes are
  generic (source labels for the judge; rewrite instead of delete) and nothing references a
  specific question. But it's still iteration on the test set, and a fresh, independent test set
  is the real check.
- My extra set was also written after seeing the system work, so it's a sanity check, not a benchmark.
- The corpus is tiny and cleanly written. 15/15 here doesn't show how it would do on long,
  overlapping or contradictory policies.
- The grounding check isn't free. It costs a second model call (more latency and cost per answer)
  and depends on a model judging another model's output. v2a showed that a badly specified check
  can remove correct information.

## Known limitations

- **The grounding check is itself a model judgement.** It can miss an unsupported claim or,
  as v2a showed, over-correct. Its rewrites are checked again, but there's no third check, and its
  verdicts vary between runs like any model output.
- **Refusal depends on the model's judgement.** There's no independent "is this answerable?" check
  besides the quote verification.
- **Small amounts of common knowledge slip in.** For example, it treats Ghana as "international
  travel" and Spain as "outside Nigeria". The grounding judge accepts these as obvious, which is
  harmless here but means the system isn't strictly closed-book.
- **Fixed top-k.** A question needing three or more documents, or a section ranked below 6, would lose
  evidence. Q11 already relies on rank 5.
- **Quote verification is strict and case-sensitive.** A correct answer whose only quote has a small
  copying error would be turned into a refusal (a "wrong refusal"). This didn't happen in any run,
  but it's the main trade-off of failing closed.
- **No conversation memory, no access control, English only.** Each question is answered on its own.
- **Needs internet** for the Anthropic API, and once for the embedding model download.
- **Non-deterministic output.** Repeated runs give different wording and different extra
  citations. In v2 the unsupported extras the model still sometimes writes are caught by the
  grounding check rather than prevented.
- **Higher latency in v2:** 4.6–10.5 s for answered questions, against 2.7–7.0 s in v1, because of the second model call.

## Project layout

```
app/
  ingest.py      split policies into one chunk per "## N." section
  retrieval.py   hybrid BM25 + bge-small embeddings, RRF fusion
  generator.py   Claude call, system prompt, JSON schema
  quotes.py      verbatim quote check (graders' normalisation rules)
  grounding.py   sentence-level grounding judge (rewrite or remove unsupported sentences)
  qa.py          retrieve -> generate -> verify quotes -> ground sentences -> refuse if unsupported
  main.py        FastAPI app: /health, /ask, contract-shaped errors
run.py           entry point (PORT env var)
data/policies/   the 10 policy documents
eval/            test questions, answer keys, evaluate.py, manual review, raw responses,
                 grounding_regression.py, archived v1/ and v2a/ results, v2b repeat runs
tests/           offline contract, quote-check and grounding tests
demo/            demo video, subtitles and the script that records it
results.csv      final results for the 15 test questions
```
